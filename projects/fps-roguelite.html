Co-op Survivor FPS

공유 길찾기와 서버 권위 상점으로 연결한 협동 서바이버 FPS

개인 프로젝트 · 2026.05 ~ 진행 중 · Unreal Engine 5.8 · C++ · GAS

GitHub 구조·설계 포트폴리오 ↗
개요담당 작업핵심 설계트러블슈팅설계 결정

개요

FPS에 서바이버의 성장 루프를 결합한 프로젝트입니다. 솔로 플레이부터 최대 4인 협동까지 지원하는 것을 목표로 합니다. 많은 적의 이동 비용을 계산하고, 인게임 상점의 판정과 재화 변경은 서버에서 처리하도록 구성했습니다.

이 포트폴리오에서는 문제와 설계 선택, 책임과 데이터 흐름, 한계와 검증을 중심으로 프로젝트를 소개합니다.

담당 작업

  • 공유 길찾기와 적 풀 구조 — 플레이어들을 시작점으로 하는 거리장, 겹친 바닥의 높이 선택, 단방향 낙하 연결, 정확한 클래스별 휴면 풀을 구성했습니다.
  • 실시간 성장 상점 — 서버의 후보·가격을 기준으로 요청을 검증하고, 재진입 차단·차감·실패 환불·개인 상태 복제를 연결했습니다.
  • 카드·무기 확장 구조 — 공유 정의와 개별 무기 상태를 나누고, 효과 사전 검사와 적용, 수정치 합성, 계산 캐시 무효화를 구성했습니다.

핵심 설계와 처리 과정

1. 개별 경로 대신 공유 거리장

출발점
적은 많고 추적 대상은 소수입니다. 비슷한 목표를 향한 계산을 적마다 반복하지 않도록 경로 계산과 적의 방향 조회를 나눴습니다.
선택과 과정
셀과 높이 레이어로 표면을 구분합니다. 플레이어가 서 있는 여러 표면에서 BFS를 시작해 거리장을 만들고, 각 적은 거리 값이 더 작은 이웃의 방향을 조회합니다. 겹친 바닥에서는 평면 좌표뿐 아니라 발 높이도 목표 표면 선택에 반영합니다.
단방향 이동
위쪽 A에서 아래쪽 B로 떨어질 수 있어도 반대로 올라갈 수는 없습니다. 목표 B에서 거리를 거꾸로 전파하려면 B로 들어오는 A를 알아야 하므로 유입 링크를 CSR 인접 목록으로 구성했습니다. 매번 모든 낙하 링크를 훑지 않도록 했습니다.
대가
균일 비용 BFS는 물리적 이동 시간이 가장 짧은 경로까지 보장하지 않습니다. 적마다 다른 비용과 목표 정책을 넣는 자유도도 줄어듭니다.

2. 실시간 상점은 서버 상태로 확정

출발점
상점 UI를 연 뒤에도 돈·거리·캐릭터·런 상태가 변합니다. Reliable RPC의 전송 보장만으로 오래된 선택이나 중복 결제를 구분할 수는 없습니다.
처리 순서
① revision·세션·후보·가격 확인 → ② 재진입 가드와 런 세대 기록 → ③ 비용 차감 → ④ 세션 재확인과 카드 적용 → ⑤ 실패 시 환불, 성공 시 같은 런에서만 후보 갱신 → ⑥ revision과 표시 상태 발행.
UI 연결
후보·잔액·가격·revision을 하나의 Snapshot으로 묶어 소유자에게만 복제합니다. 호스트의 발행과 클라이언트의 복제 알림이 같은 변경 이벤트를 사용합니다.
대가
오래된 UI에서 보낸 요청을 거부한 뒤에는 새 상태를 보여줘야 합니다. 환불은 재화에 대한 보상 처리이며 임의의 카드 부작용을 모두 되돌리는 데이터베이스 트랜잭션은 아닙니다.

3. 효과 확장과 수치 계산을 분리

출발점
카드 종류마다 중앙 함수를 늘리거나, 공통 무기 정의에 개인 업그레이드를 저장하면 변경 범위와 상태 혼입 위험이 커집니다.
처리 순서
카드 정의의 모든 효과를 사전 검사한 뒤 적용합니다. 기본값은 DataAsset, 탄약·장전·특정 무기 수정치는 인스턴스, 전체 무기 수정치는 PlayerState에 둡니다. 적용 성공 뒤 획득 기록을 남깁니다.
계산 시점
입력이 바뀌면 캐시를 무효화하고 다음 수치 조회에서 다시 계산합니다. 변경이 없는 반복 조회는 결과를 재사용합니다. 복제된 입력에서 최종 값을 계산하며 캐시 자체를 복제하지 않습니다.
대가
효과 종류는 파생 클래스로 확장할 수 있지만 새 스탯 축을 추가할 때는 합성 함수도 수정해야 합니다. 무효화 경로를 빠뜨리면 오래된 값이 남습니다.

설계 전제

  • 일반 적은 경량 체력·풀링·공유 길찾기를 사용합니다. GAS 적용 범위는 플레이어·엘리트·보스로 나눕니다.
  • 성장 선택은 코인 상점에서 처리하며 개인의 구매가 전체 게임을 멈추지 않도록 설계합니다.
  • 판정과 재화 변경은 서버가 담당하고 클라이언트는 입력과 UI를 전달합니다.

문제 발생 상황과 해결 과정

실제 수정 기록과 회귀 검증 시나리오를 구분했습니다.

1. 타워 가장자리에서 층 선택과 적 이동이 어긋남

기록 구분
실제 수정 이력 · b19cd92c (타워 길찾기 수정).
발생 상황
플레이어가 타워 가장자리 바깥에 서면 해당 셀에 발 높이와 맞는 표면이 없을 수 있었습니다. 적도 유효 표면이 없는 셀에서 타워 중심으로 직진하거나, 올라설 수 없는 벽에 막혀 멈추는 상황을 다뤘습니다.
원인과 추적
플레이어 목표를 셀의 지면 순위로 잡는 경로와, 표면을 못 찾은 적의 직진 대체 동작을 구분했습니다. 목표 표면 선택과 막힌 적의 이동 대응을 각각 수정 대상으로 나눴습니다.
수정
가까운 표면 탐색을 플레이어의 발 높이에서 시작하고 같은 층·시야 조건을 우선했습니다. 적은 이웃의 방향을 빌려 쓰며, 올라설 수 없는 벽에서는 바닥 평면에 투영한 벽면 방향으로 움직이게 했습니다. 허용 경사보다 가파른 탈출 이웃은 제외하고 단방향 낙하 연결을 추가했습니다.

2. 같은 구매를 재요청하거나 효과 적용이 거부됨

기록 구분
현재 구현의 실패 처리와 회귀 검증 시나리오.
재현 조건
한 번 성공한 구매의 revision으로 다시 요청합니다. 별도로 잘못된 후보 인덱스와 적용할 수 없는 카드를 요청합니다.
원인 경계
UI의 선택은 서버 최신 상태보다 늦을 수 있습니다. 효과 콜백은 거래를 다시 요청하거나 원래 후보 배열·런 상태를 바꿀 수도 있습니다.
처리
revision과 세션을 검사하고 재진입을 차단합니다. 카드 값은 적용 전에 복사하며 차감 뒤에도 세션과 런 세대를 확인합니다. 적용 거부 시 환불하고 기존 후보를 보존합니다.

설계 결정

길찾기 규모와 계산량

수치·규칙
현재 높이 레이어는 2개이며, 표면 V개와 연결 E개에 대한 BFS의 시간 복잡도는 O(V+E)입니다.
판독 기준
문서에서 확인한 구조와 알고리즘 복잡도입니다. 적 한 마리의 조회와 전체 재계산을 구분합니다.
한계
같은 셀에 3개 이상의 층을 표현하는 데 제약이 있습니다.

카드 적용 단계

수치·규칙
효과 목록을 2회 순회합니다. 전체 효과를 사전 검사한 뒤 적용합니다.
판독 기준
효과가 n개라면 기본 순회에서는 n개의 효과를 검사하고 적용합니다. 개별 효과 내부의 비용은 별도입니다.
한계
선행 효과가 후행 효과의 전제를 깨면 부분 적용 문제가 남습니다.
