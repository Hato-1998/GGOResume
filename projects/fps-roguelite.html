ART: Arcade Reclamation Team

오염된 픽셀 아케이드 세계를 되찾는 1~4인 협동 FPS 로그라이트 호드 슈터

개인 프로젝트 · 2026.05 ~ 2026.10 공개 데모 · Unreal Engine 5.8 · C++ · GAS · 개발 코드명 FPSRoguelite

개요담당 작업핵심 설계트러블슈팅AI 협업검증 범위

개요

오염된 구역을 복구 장치로 하나씩 되찾으며 몰려오는 적을 막고, 20:00에 등장하는 최종 보스를 처치하는 협동 FPS입니다. 2026년 10월 공개 데모를 완성했으며 Steam 스토어 페이지는 심사 중입니다. 데모 한 판은 런 시작, 전투·파밍·무기 성장, 20:00 최종 보스, 승리/패배, 결산으로 이어지고 솔로부터 4인 협동까지 지원합니다.

게임 판정은 서버가 담당하고 화면 연출은 각 기기에서 처리합니다. 이 포트폴리오에서는 문제와 설계 선택, 서버 상태와 표현의 경계, 한계와 검증을 중심으로 프로젝트를 소개합니다.

담당 작업

  • 공유 길찾기와 적 풀 구조: 플레이어들을 시작점으로 하는 거리장, 겹친 바닥의 높이 선택, 단방향 낙하 연결, 정확한 클래스별 휴면 풀을 구성했습니다.
  • 구역 복구 체인: 구역 상태를 서버가 판정해 복제하고, 어둠·하늘·경계 연출은 복제 값을 읽는 로컬 표현으로 분리했습니다. 구역 복구 완료는 무기 보상과 연결됩니다.
  • 무기 성장과 공급: 피해를 낸 무기 인스턴스에 경험치를 쌓고, 5레벨마다 서버가 Perk를 자동 장착합니다. 코인·자판기 경로를 걷어내고 처치·구역 복구·미션 보상을 하나의 공유 실물 생성기로 통합했습니다.
  • 협동 관전과 원격 표현: 쓰러진 플레이어가 아군을 1인칭으로 관전하도록 대상 전환만 서버에서 검증하고, 팔·무기·탄 표현은 기존 복제 상태로 로컬 재생했습니다.

핵심 설계와 처리 과정

1. 개별 경로 대신 공유 거리장

출발점
적은 많고 추적 대상은 소수입니다. 비슷한 목표를 향한 계산을 적마다 반복하지 않도록 경로 계산과 적의 방향 조회를 나눴습니다.
선택과 과정
셀과 높이 레이어로 표면을 구분합니다. 플레이어가 서 있는 여러 표면에서 BFS를 시작해 거리장을 만들고, 각 적은 거리 값이 더 작은 이웃의 방향을 조회합니다. 위에서 아래로만 떨어질 수 있는 연결은 유입 링크를 CSR 인접 목록으로 구성해 역방향 전파에 반영했습니다.
대가
균일 비용 BFS는 물리적 이동 시간이 가장 짧은 경로까지 보장하지 않습니다. 장애물 뒤에서 적이 한 줄로 모이는 현상은 시야 직진 패스로 1단계 완화했고, 남은 부분은 후속 판단으로 두었습니다.

2. 구역 상태는 서버, 연출은 각 기기

출발점
"들어와서 무엇을 해야 할지 모르겠다"는 플레이 피드백이 있었습니다. 생존 시간 외에 중간 목표가 필요했습니다.
선택과 과정
오염된 구역을 복구 장치로 되찾아 보스전 공간을 넓히는 것을 런의 1차 목표로 정했습니다. 구역 상태와 장치 진행은 서버가 판정하고 GameState로 복제합니다. 어둠·하늘·경계는 픽셀의 월드 위치로 구역을 찾는 공용 재질과 후처리 한 패스로 그려 구역마다 재질이나 액터를 늘리지 않았습니다.
대가
장치 조작은 플레이 테스트를 거치며 반경 체류, 구역 체류, 복구 구역 한정 순서로 바뀌었습니다. 조정값은 코드가 아닌 데이터로 두었습니다.

3. 화폐 없이 전투로 강해지는 무기

출발점
코인을 거치면 "잡았다 → 돈을 얻었다 → 자판기에서 샀다 → 강해졌다"로 인과가 길어집니다. 데모에 남은 코인의 용도도 무기 자판기 하나뿐이었습니다.
선택과 과정
경험치는 실제로 줄어든 체력을 표준 DPS로 나눈 값이며 피해를 낸 무기 인스턴스에 귀속합니다. 5레벨마다 서버가 호환 Perk를 추첨해 원장 트랜잭션으로 장착하고, 클라이언트는 버리기·교체 결정만 요청합니다. 무기는 처치(등급별 확률)·구역 복구 완료·비행 표적 미션 보상에서 공유 실물로 나오며 출처별 품질 분포만 다릅니다.
대가
구매 선택이 사라진 대신 바닥 무기 수명·상한과 출처별 분포를 플레이로 조정해야 합니다. Perk 결정 RPC와 대기 Perk 복제는 서버 권위 경로라 독립 계획·머지 검토를 거쳤습니다.

4. 복제하지 않는 1인칭 관전

출발점
1인칭 팔·무기는 소유자 기기에서만 그리는 로컬 표현이었습니다. 쓰러진 플레이어가 아군을 1인칭으로 보려면 이 전제의 예외가 필요했습니다.
선택과 과정
클라이언트는 이전/다음 방향만 보내고 서버가 다운 상태·쿨다운·대상 생존을 검사합니다. 관전자 기기는 이미 복제되는 조준·무기·사격 이벤트로 팔·무기·트레이서를 재생합니다. 팀원 아이템 표시는 정의와 개수만 담은 표시용 사본을 복제하고 원본은 소유자 전용으로 유지했습니다.
대가
"직접 조종 중일 때만 동작"하는 전제가 카메라·애니메이션·무기·탄 표현에 각각 있어 층별로 찾아 고쳐야 했습니다.

문제 발생 상황과 해결 과정

실제 수정 기록과 검증 범위를 구분했습니다.

1. 멀티플레이에서만 구역 색이 깜빡임

발생 상황
멀티플레이 입장 직후 맵 전체가 복구된 색으로 보이다가 잠시 뒤 오염 구역이 어두워졌습니다. 싱글플레이에서는 재현되지 않았습니다.
원인과 추적
서버가 초기 구역 상태를 런 봉인(전원 로딩 완료 또는 타임아웃) 시점에만 커밋했습니다. 동기화 플래그 하나가 "구역 상태를 안다"와 "런이 시작됐다"라는 두 사실을 함께 뜻하고 있었습니다.
수정
GameState를 얻는 즉시 초기 상태를 커밋하고, 런 시작 여부는 이미 복제되는 봉인 여부로 따로 판정했습니다. 봉인 전에는 장치 진행과 상호작용을 막았습니다. 독립 검토 지적을 반영했고 관련 자동화 58/58 통과와 사용자 멀티 확인으로 증상이 사라진 것을 확인했습니다.

2. 낙하 경계에서 슬라이드가 멈춤

발생 상황
낙하 경계로 슬라이드해 들어가면 진입 각도에 따라 슬라이드가 멈추거나 가장자리를 따라 미끄러졌습니다.
원인과 추적
엔진 CharacterMovementComponent의 앉기·낙하 분기를 추적해, 앉은 상태에서 가장자리 낙하를 막는 기본 설정이 이동을 되돌린다는 점을 확인했습니다.
수정
코드를 늘리지 않고 기존 설정 변경으로 해결했습니다. 풀 리빌드·자동화 58/58과 사용자 PIE 네 가지 동작으로 확인했습니다.

AI 협업 개발 방식

구현의 상당 부분을 AI 에이전트가 맡았습니다. 아래는 그 결과물을 통제하고 검증한 방식입니다. 생산성은 측정 기록이 없어 수치로 주장하지 않습니다.

역할 분리와 위험도별 게이트

역할
게임 규칙·범위·통합·체감 판정은 본인이 결정합니다. 계획과 최종 검증은 상위 모델, 명세 범위 안의 구현은 구현 모델이 맡고, 독립 검토 모델은 지적만 제출합니다.
게이트
서버 권위·복제, 스웜 핫패스, 수명주기·소유권 구조를 바꾸는 고위험 변경에만 독립 계획 검토(G1)와 병합 전 적대 검토(G2)를 둡니다. 머지 차단 지적이 남으면 푸시하지 않습니다. 그 밖의 변경은 빌드·관련 시험·diff 검토로 마칩니다.
작업 명세
구현 담당, 허용 파일, 완료 조건, 인계 조건을 적습니다. 명세와 코드가 충돌하거나 명세에 없는 권한·복제 변경이 필요하거나 같은 실패가 두 번 반복되면 구현을 멈추고 상위 모델에 넘깁니다.

보고는 주장으로 보고 직접 검증

검증 규율
빌드는 종료 코드가 아니라 로그의 Result 줄로 판정합니다. 기존 실패 시험은 기준 커밋과 이름 단위로 대조해 새 실패 0건을 확인합니다. 인계 메모의 수식은 다시 계산하고, 동작과 외형은 직접 플레이로 확인합니다.
검토가 바꾼 결과
원격 투사체 설계에서 기존 순간이동 판정이 클라이언트 외삽과 양립하지 않는다는 지적을 받아 복제 비행 번호 방식으로 바꿨습니다. 무기 보상 미션은 보상이 지붕 위에 떨어지는 지적을 받아 가장 낮은 걷기 가능 바닥을 찾게 했습니다.
기록
결정 로그 190건, 구조 결정 문서 48건, 설계 토론 기록 129건을 남기고 새 계획 전에 먼저 조회합니다. 작업 보드에 착수를 클레임하고 완료 커밋으로 마감합니다.

검증 범위

확인한 것과 남은 것

확인함
작업별 빌드·관련 자동화 시험과 2인 PIE 확인 기록, 고위험 변경의 독립 계획·머지 검토, 과거 패키지 측정(약 890마리, 로컬 4인 호스트)에서 확인한 게임 스레드 병목.
남음
4인 원격 네트워크 실플레이, 20분 런 후반의 장시간 성능, 적 1000+ 스트레스 목표의 현재 빌드 실측은 별도 검증 대상입니다.
판독 기준
설계 승인, 코드 구현, 실행 검증은 서로 다른 주장으로 구분합니다. 시험 개수를 합쳐 게임 전체의 완성도로 해석하지 않습니다.
