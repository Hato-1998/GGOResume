Co-op Survivor FPS

공유 길찾기와 서버 권위 상점으로 연결한 협동 서바이버 FPS

개인 프로젝트 · 2026.05 ~ 진행 중 · Unreal Engine 5.8 · C++ · GAS

GitHub 구조·설계 포트폴리오 ↗
개요담당 작업핵심 설계구조트러블슈팅수치와 근거한계

개요

직접 조준하고 쏘는 1인칭 전투에 서바이버의 성장 루프를 결합한 프로젝트입니다. 솔로부터 최대 4인 협동을 목표로, 많은 적의 이동 비용을 공유하고 실시간 상점의 판정과 재화 변경을 서버에 모았습니다.

프로그래밍 포트폴리오는 문제와 설계 선택, 책임과 데이터 흐름, 한계와 검증을 중심으로 소개합니다.

담당 작업

  • 공유 길찾기와 적 풀 구조 — 플레이어들을 시작점으로 하는 거리장, 겹친 바닥의 높이 선택, 단방향 낙하 연결, 정확한 클래스별 휴면 풀을 구성했습니다.
  • 실시간 성장 상점 — 서버의 후보·가격을 기준으로 요청을 검증하고, 재진입 차단·차감·실패 환불·개인 상태 복제를 연결했습니다.
  • 카드·무기 확장 구조 — 공유 정의와 개별 무기 상태를 나누고, 효과 사전검사와 적용, 수정치 합성, 계산 캐시 무효화를 구성했습니다.
  • 회귀 검증 지점 분리 — 월드 전체를 띄우지 않고도 표면 선택과 클래스별 풀, 거래 실패 조건을 검사할 수 있도록 계산·규칙 경계를 나눴습니다.

개인 프로젝트이며 생성형 AI를 개발 도구로 활용했습니다. 엔진이 제공하는 GAS·복제·Subsystem을 기반으로 프로젝트의 규칙과 연결 구조를 구현했습니다.

핵심 설계와 처리 과정

1. 개별 경로 대신 공유 거리장

출발점
적은 많고 추적 대상은 소수입니다. 비슷한 목표를 향한 계산을 매 적마다 반복하지 않도록 경로 계산과 적의 방향 조회를 나눴습니다.
선택과 과정
셀과 높이 레이어로 표면을 구분합니다. 플레이어가 서 있는 여러 표면에서 BFS를 시작해 거리장을 만들고, 각 적은 더 낮은 거리의 이웃 방향을 조회합니다. 겹친 바닥에서는 평면 좌표뿐 아니라 발 높이가 목표 표면 선택에 참여합니다.
단방향 이동
위쪽 A에서 아래쪽 B로 떨어질 수 있어도 반대로 올라갈 수는 없습니다. 목표 B에서 거리를 거꾸로 전파하려면 B로 들어오는 A를 알아야 하므로 유입 링크를 CSR 인접 목록으로 구성했습니다. 매번 모든 낙하 링크를 훑지 않도록 했습니다.
대가
균일 비용 BFS는 물리적 이동 시간이 가장 짧은 경로까지 보장하지 않습니다. 적마다 다른 비용과 목표 정책을 넣는 자유도도 줄어듭니다.

2. 실시간 상점은 서버 상태로 확정

출발점
상점 UI를 연 뒤에도 돈·거리·캐릭터·런 상태가 변합니다. Reliable RPC의 전송 보장만으로 오래된 선택이나 중복 결제를 구분할 수는 없습니다.
처리 순서
① revision·세션·후보·가격 확인 → ② 재진입 가드와 런 세대 기록 → ③ 비용 차감 → ④ 세션 재확인과 카드 적용 → ⑤ 실패 시 환불, 성공 시 같은 런에서만 후보 갱신 → ⑥ revision과 표시 상태 발행.
UI 연결
후보·잔액·가격·revision을 하나의 Snapshot으로 묶어 소유자에게만 복제합니다. 호스트의 발행과 클라이언트의 복제 알림이 같은 변경 이벤트를 사용합니다.
대가
오래된 UI에서 보낸 요청은 거부 후 새 상태를 보여줘야 합니다. 환불은 재화에 대한 보상 처리이며 임의의 카드 부작용을 모두 되돌리는 데이터베이스 트랜잭션은 아닙니다.

3. 효과 확장과 수치 계산을 분리

출발점
카드 종류마다 중앙 함수를 늘리거나, 공통 무기 정의에 개인 업그레이드를 저장하면 변경 범위와 상태 혼입 위험이 커집니다.
처리 순서
카드 정의의 모든 효과를 먼저 사전검사한 뒤 적용합니다. 기본값은 DataAsset, 탄약·장전·특정 무기 수정치는 인스턴스, 전체 무기 수정치는 PlayerState에 둡니다. 적용 성공 뒤 획득 기록을 남깁니다.
계산 시점
입력이 바뀌면 캐시를 무효화하고 다음 수치 조회에서 다시 계산합니다. 변경이 없는 반복 조회는 결과를 재사용합니다. 복제된 입력에서 최종 값을 계산하며 캐시 자체를 복제하지 않습니다.
대가
효과 종류는 파생 클래스로 확장할 수 있지만 새 스탯 축은 합성 함수도 수정해야 합니다. 무효화 경로를 빠뜨리면 오래된 값이 남습니다.

설계 전제

  • 일반 적은 경량 체력·풀링·공유 길찾기를 사용합니다. GAS 적용 범위는 플레이어·엘리트·보스로 나눕니다.
  • 성장 선택은 코인 상점에서 처리하며 개인의 구매가 전체 게임을 멈추지 않도록 설계합니다.
  • 판정과 재화 변경은 서버가 담당하고 클라이언트는 입력과 UI를 전달합니다.
  • 동시 적 1,000은 설계상 최악 상한 목표입니다. 해당 규모의 FPS·네트워크 성능을 달성했다는 실측값은 제시하지 않습니다.

구조 한눈에 보기

  1. 입력·UI클라이언트에서 구매·게임플레이 요청
  2. 서버 규칙소유 객체의 RPC를 통해 요청 검증과 상태 변경
  3. 개인 상태와 월드PlayerState의 ASC·지갑, 월드 서브시스템의 카드·스폰·길찾기
  4. 상태 전달복제 상태와 RepNotify를 통해 UI 갱신

DataAsset은 무기·카드·상점의 정의를 제공합니다. 위 순서는 책임과 상태 흐름을 요약한 개념도입니다.

문제 발생 상황과 해결 과정

실제 수정 기록과 회귀 검증 시나리오를 구분했습니다. 아래 기대 결과를 이번 페이지 편집에서 새로 실행한 테스트 결과로 표기하지 않습니다.

1. 타워 가장자리에서 층 선택과 적 이동이 어긋남

기록 구분
실제 수정 이력 · b19cd92c (타워 길찾기 수정).
발생 상황
플레이어가 타워 가장자리 바깥에 서면 해당 셀에 발 높이와 맞는 표면이 없을 수 있었습니다. 적도 유효 표면이 없는 셀에서 타워 중심으로 직진하거나, 올라설 수 없는 벽에 막혀 멈추는 상황을 다뤘습니다.
원인과 추적
플레이어 목표를 셀의 지면 순위로 잡는 경로와, 표면을 못 찾은 적의 직진 대체 동작을 구분했습니다. 목표 표면 선택과 막힌 적의 이동 대응을 각각 수정 대상으로 나눴습니다.
수정
가까운 표면 탐색을 플레이어의 발 높이에서 시작하고 같은 층·시야 조건을 우선했습니다. 적은 이웃의 방향을 빌려 쓰며, 올라설 수 없는 벽에서는 바닥 평면에 투영한 벽면 방향으로 움직이게 했습니다. 허용 경사보다 가파른 탈출 이웃은 제외하고 단방향 낙하 연결을 추가했습니다.
확인과 한계
해당 커밋에는 TowerPath 자동화 테스트와 사용자 플레이테스트 기록이 있습니다. 2×1 합성 그리드의 지면·데크 선택도 회귀 시나리오로 설명합니다. 통과 횟수나 전후 프레임 시간 원시 자료는 이 페이지에서 제시하지 않습니다.

2. 같은 구매를 재요청하거나 효과 적용이 거부됨

기록 구분
현재 구현의 실패 처리와 회귀 검증 시나리오. 실제 재화 손실 사고가 발생했다고 단정하지 않습니다.
재현 조건
한 번 성공한 구매의 revision으로 다시 요청합니다. 별도로 잘못된 후보 인덱스와 적용할 수 없는 카드를 요청합니다.
원인 경계
UI의 선택은 서버 최신 상태보다 늦을 수 있습니다. 효과 콜백은 거래를 다시 요청하거나 원래 후보 배열·런 상태를 바꿀 수도 있습니다.
처리
revision과 세션을 검사하고 재진입을 차단합니다. 카드 값은 적용 전에 복사하며 차감 뒤에도 세션과 런 세대를 확인합니다. 적용 거부 시 환불하고 기존 후보를 보존합니다.
기대 결과
중복·잘못된 인덱스 요청의 추가 차감은 0이어야 합니다. 적용 거부 시 순재화 변화는 0이어야 합니다. 이는 검증 조건이며 실제 지연·패킷 손실을 포함한 다중 클라이언트 시험 결과는 아닙니다.

3. 풀에서 상속 관계의 다른 적 클래스가 섞이는 경우

기록 구분
정확한 클래스 반환 계약을 확인하는 회귀 시나리오.
재현 조건
일반 적만 넣은 풀에서 엘리트를 요청하고, 반대로 엘리트만 넣은 풀에서 일반 적을 요청합니다.
설계와 처리
상속 허용 여부가 아니라 정확한 클래스별 버킷에서만 취득합니다. 무효 슬롯은 제거하고 총량이 다른 클래스에 치우치면 가장 큰 다른 휴면 버킷에서 하나를 축출합니다. 파괴와 총량 회계는 스폰 서브시스템이 담당합니다.
기대 결과와 한계
다른 클래스 반환은 0건이어야 하며 요청한 타입이 없으면 취득에 실패해야 합니다. 클래스별 용량 불균형과 잦은 축출은 별도 비용이고, 액터 재활성화·복제 수명주기는 추가 확인 대상입니다.

정량적으로 읽는 설계 결정

길찾기 규모와 계산량

수치·규칙
현재 높이 레이어 2개. 표면 V개와 연결 E개에 대한 BFS는 O(V+E).
판독 기준
문서에서 확인한 구조와 알고리즘 복잡도입니다. 적 한 마리의 조회와 전체 재계산을 구분합니다.
한계
같은 셀에 3개 이상의 층을 표현하는 데 제약이 있습니다. 조회가 가볍다는 사실이 전체 프레임 성능을 보장하지 않습니다.

풀 취득 비용

수치·규칙
클래스 해시 조회는 평균 O(1). 무효 슬롯 k개가 연속되면 취득 시 그만큼 순회.
판독 기준
정확한 클래스 버킷을 선택하는 비용과 유효 객체를 꺼내는 비용을 나눠 설명합니다.
한계
취득 전체의 최악 비용을 O(1)로 주장하지 않습니다. 축출 버킷 선택은 클래스 수에 비례합니다.

무기 수치 합성

수치·규칙
(기본값 + 가산값 합) × (1 + 비율값 합). 탄창 최소 1, FOV 5~170도.
판독 기준
예시로 기본값 100, 가산값 20, 비율 10%이면 제한 적용 전 132입니다. 설계 공식의 설명용 계산이며 실제 무기 밸런스 값은 아닙니다.
한계
스탯마다 후처리 제한과 제외 축이 다릅니다. 한 예시로 모든 스탯의 동작을 일반화하지 않습니다.

카드 적용 단계

수치·규칙
효과 목록을 2회 순회: 전체 사전검사 후 효과 적용.
판독 기준
효과가 m개라면 기본 순회는 m개 검사와 m개 적용입니다. 개별 효과 내부의 비용은 별도입니다.
한계
선행 효과가 후행 효과의 전제를 깨면 부분 적용 문제가 남습니다. 완전한 원자성을 보장하지 않습니다.

타워 낙하 설정과 베이크 기록

수치·규칙
수정 당시 최대 낙하 높이 6,000cm, 0은 비활성. L_Map_1 재베이크에 낙하 비트 387개 기록.
판독 기준
b19cd92c의 특정 시점 설정·콘텐츠 기록입니다. 현재 모든 맵의 연결 수나 성능 측정치가 아닙니다.
한계
비트 수를 적 수·프레임 수로 해석할 수 없습니다. 지형이나 베이크가 바뀌면 다시 확인해야 합니다.

부하 목표

수치·규칙
동시 적 1,000은 설계상 최악 상한 목표. 협동 인원 목표는 1~4인.
판독 기준
목표치와 달성 실측을 구분합니다. 재현 가능한 원시 성능 자료는 현재 공개하지 않았습니다.
한계
FPS·개선율을 기재하지 않습니다. 하드웨어, 패키지 설정, 활성 적 수, 접속 인원, 프레임 시간·네트워크 지표를 함께 측정해야 합니다.

알려진 한계와 검증 범위

  • 높이 레이어·동적 장애물·베이크 좌표계·단방향 낙하는 각각 검증해야 합니다. 길찾기 공유가 충돌·렌더링·복제 비용까지 없애지는 않습니다.
