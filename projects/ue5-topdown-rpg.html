GAS 전투에서 입력·UI·체크포인트 저장까지 이어지는 RPG 구조

개인 학습 프로젝트 · 2026.03 ~ 05 · Unreal Engine 5.7 · C++ · GAS

GitHub 구조·설계 포트폴리오 ↗
개요담당 작업핵심 설계구조트러블슈팅수치와 근거한계

개요

GAS 기반 전투와 캐릭터 성장, 스킬 메뉴, 체크포인트 저장을 연결한 탑다운 RPG입니다. Stephen Ulibarri의 Unreal Engine 5 - Gameplay Ability System - Top Down RPG 강의를 기반으로 학습하고, 저장·데이터·입력의 책임을 서브시스템과 컴포넌트로 분리했습니다.

플레이 영상 보기 ↗

담당 작업과 학습 기반

  • 강의 기반 전투·성장 연결 — GAS 전투, 속성·경험치·스킬 진행, HUD·성장 메뉴와 체크포인트를 학습하고 프로젝트에 연결했습니다.
  • 저장 책임 분리 — GameMode·Character에 흩어진 슬롯·진행·월드 저장 흐름을 SaveGameSubsystem으로 모으고, GUID 식별과 목적지 맵 검증을 추가했습니다.
  • 입력 기능 분리 — 커서 타기팅·클릭 이동·마법진·피해 숫자를 4개 ActorComponent로 분리하고 PlayerController에 입력 조정 역할을 남겼습니다.
  • 데이터와 화면 경계 정리 — 공통 데이터 조회·캐싱을 GameDataSubsystem으로 모으고, HUD의 WidgetController와 로드 화면 MVVM의 역할을 나눴습니다.

Stephen Ulibarri의 GAS Top Down RPG 강의가 기반입니다. 강의·엔진의 제공 기능과 저장·입력 책임을 분리한 작업을 구분하며 전체를 독자 개발한 시스템으로 소개하지 않습니다.

핵심 설계와 처리 과정

1. 전투 상태의 소유자와 행동 주체 구분

설계 과제
현재 월드에서 움직이는 캐릭터와 플레이어의 성장 상태는 역할이 다릅니다. 피해 공식과 화면 표시가 여러 스킬에 흩어지지 않도록 공통 경로도 필요했습니다.
구성과 순서
PlayerState가 ASC·AttributeSet을 소유하고 Character를 행동 주체로 연결합니다. 입력 태그를 능력에 전달한 뒤 GameplayAbility가 대상·피해 매개변수를 구성하고, GameplayEffect·ExecCalc가 피해를 계산합니다. AttributeSet의 상태 변경을 UI와 연출에 전달합니다.
초기화 경계
서버 빙의 시점과 클라이언트의 PlayerState 수신 시점에서 Owner·Avatar 연결을 확인해야 합니다. 상태가 준비되기 전에 UI가 구독하면 최초 값이나 알림을 놓칠 수 있습니다.
대가
태그·데이터·효과 간 연결이 늘어납니다. 계수 누락 시 기본값과 로그로 계속 동작하더라도 의도한 밸런스까지 보장하지는 않습니다.

2. 저장 요청과 파일·월드 처리를 분리

변경 전
GameMode와 Character에 슬롯 처리, 진행 저장, 월드 직렬화, 맵 이동 흐름이 모여 있었습니다. 로드 화면과 플레이 중 저장이 같은 정책을 사용하기 어려웠습니다.
변경 과정
슬롯 생성·조회·삭제와 진행 저장을 GameInstanceSubsystem으로 이동했습니다. SaveInterface 액터만 수집해 맵별 ID·이름·Transform·저장 속성을 기록합니다. 로드 시 ID 인덱스를 만들고 기존 월드 액터와 대응한 뒤 선택적 위치 복원, 역직렬화, 복원 콜백 순으로 처리합니다.
호환 경로
GUID 기반 매칭을 우선하고, ID가 없는 이전 저장 데이터에는 이름 조회를 남겼습니다. 위치를 복원할지는 액터가 인터페이스로 결정합니다.
대가
GameMode의 저장 클래스·맵 목록 설정 의존은 남아 있습니다. 동기 파일 기록은 순서를 단순화하지만 저장량이 커지면 프레임을 멈출 수 있습니다.

3. 입력 컴포넌트와 화면별 UI 연결

변경 전
한 Controller가 커서 Trace, 자동 이동, 마법진, 피해 숫자, 능력 입력까지 처리해 한 기능 수정의 영향 범위가 넓었습니다.
변경 과정
클릭 이동·커서 대상·마법진·피해 숫자를 분리했습니다. Controller는 입력 상태와 대상에 따라 이동을 중단하거나 능력 입력을 전달합니다. 전투 HUD와 성장 메뉴는 WidgetController가 값·이벤트를 전달하고, 로드 화면 ViewModel은 슬롯 표시·선택을 관리합니다.
저장 연결
ViewModel은 파일을 직접 쓰지 않고 SaveGameSubsystem에 슬롯 작업과 이동을 요청합니다. 화면 표시와 저장 정책의 변경 위치를 구분했습니다.
대가
컴포넌트 수와 연결 지점은 늘어납니다. Controller의 조정 책임과 UI 초기 바인딩·구독 해제·재진입 검증이 여전히 필요합니다.

설계 전제

  • 스킬 실행은 GameplayAbility, 수치 변화는 GameplayEffect·AttributeSet을 중심으로 구성합니다.
  • 캐릭터 기본값·스킬 정보·레벨별 계수는 DataAsset과 테이블로 관리합니다.
  • HUD와 로드 화면은 목적에 맞춰 WidgetController와 MVVM을 각각 사용합니다.
  • 현재 저장 경로는 동기 방식이며 기존 배치 액터의 상태를 복원합니다. 비동기 저장 큐나 일반적인 동적 액터 재생성 시스템으로 설명하지 않습니다.

구조 한눈에 보기

  1. 입력 의도Enhanced Input·GameplayTag를 PlayerController에서 조정
  2. 전투·속성PlayerState의 ASC를 거쳐 스킬·효과·피해 계산 수행
  3. 화면 반영AttributeSet 변경을 WidgetController가 HUD와 성장 메뉴에 전달
  4. 진행 저장체크포인트·로드 화면이 SaveGameSubsystem을 통해 슬롯과 맵별 상태 관리

문제 발생 상황과 해결 과정

저장 문제와 Controller 리팩토링은 원본 프로젝트의 작업 기록에 근거합니다. 당시 결과와 이번 문서의 정적 확인 범위를 구분했습니다.

1. 두 번째 던전에서 저장 후 재시작하면 진행이 초기화됨

증상
두 번째 던전으로 이동해 저장하고 재시작했을 때 슬롯 진행이 초기화된 것처럼 보였습니다.
원인 추적
파일 삭제, 데이터 손상, 저장 순서 문제를 나눠 조사했습니다. 런타임 로그와 SaveGames 폴더 상태를 확인하고 슬롯 생성·월드 저장·플레이어 진행 저장·맵 이동의 호출 순서를 추적했습니다.
확인한 원인
맵 이동 직전에 같은 슬롯을 대상으로 여러 비동기 저장 호출이 겹쳐 저장 순서가 꼬일 수 있었습니다.
수정
핵심 저장을 동기 슬롯 기록으로 바꾸고 목적지 맵 등록 여부를 검증했습니다. 저장 흐름과 실패 로그를 SaveGameSubsystem에 모았습니다.
당시 결과와 한계
원본 작업 기록은 던전 이동과 재시작 후 진행 데이터 유지를 보고합니다. 이번 편집에서는 재실행하지 않았으며 재현 횟수·저장 시간·실패율 전후 수치는 기록에 없어 제시하지 않습니다.

2. 배치 액터의 이름에 의존하는 세이브 매칭

문제 조건
저장 대상 액터를 이름만으로 대응시키면 에디터에서 이름이나 배치를 수정할 때 기존 저장과의 연결이 깨질 수 있습니다.
설계 변경
영속 GUID를 저장 식별자로 사용하고, 로드할 때 ID 인덱스를 먼저 구성합니다. ID가 없는 이전 데이터는 별도의 이름 기반 경로로 대응시킵니다.
확인할 결과
이름을 바꿔도 같은 GUID의 배치 액터에 상태가 적용되는지, ID 없는 이전 데이터가 이름 경로로 복원되는지 나눠 확인해야 합니다. ID 중복·누락은 따로 검사해야 합니다.
한계
현재 월드에 존재하는 액터를 찾아 적용합니다. 임의의 동적 생성 액터를 전부 다시 만드는 범용 저장 기능은 아닙니다. 이 항목은 호환성 설계와 검증 조건이며 버그 재현 횟수는 제공하지 않습니다.

3. Controller 기능 확장 시 관련 없는 로직까지 수정

상황
커서 판독, 이동, 타기팅 표시, 피해 숫자, 능력 입력이 하나의 Controller에 모여 있었습니다.
분석과 수정
입력을 조정하는 역할과 실제 동작을 나눴습니다. 커서 타기팅·클릭 이동·마법진·피해 숫자를 각각 ActorComponent로 옮기고, Controller는 입력 이벤트를 받아 위임하도록 정리했습니다.
구조에서 확인되는 결과
입력 세부 동작의 변경 위치가 4개 컴포넌트로 나뉩니다. Controller는 대상 판독과 입력 상태에 따른 조정 책임을 유지합니다.
한계
분리 개수는 확인 가능하지만 작업 시간이나 결함률 감소를 측정한 수치는 없습니다. 컴포넌트 간 의존과 초기화 순서까지 사라진 것은 아닙니다.

정량적으로 읽는 설계 결정

입력 기능의 분리 단위

수치·규칙
4개 ActorComponent: 클릭 이동, 커서 타기팅, 마법진, 피해 숫자.
판독 기준
클래스와 책임의 개수입니다. 변경 위치를 구분한 구조적 결과로 읽습니다.
한계
4개로 나눴다는 사실이 성능 향상이나 수정 시간 단축을 수치로 증명하지는 않습니다.

로드 화면 슬롯

수치·규칙
현재 로드 화면에 3개의 명명된 슬롯 필드.
판독 기준
UI의 구체적인 슬롯 구성을 확인한 값입니다. 저장 서비스의 보편적인 최대 용량이 아닙니다.
한계
4개 이상으로 확장하려면 서비스 설정뿐 아니라 ViewModel·화면 구성도 검토해야 합니다.

화면 연결 방식

수치·규칙
2가지: 전투·성장 화면의 WidgetController, 로드 화면의 MVVM.
판독 기준
같은 게임 상태를 표시하더라도 화면의 목적에 따라 연결 방식을 구분했습니다.
한계
프로젝트 전체 UI가 MVVM이라는 표현은 부정확합니다. 두 경로 각각의 초기값·구독·재진입 검증이 필요합니다.

저장 식별과 호환

수치·규칙
GUID 우선 매칭, ID 없는 이전 데이터의 이름 매칭이라는 2개 경로.
판독 기준
현재 데이터와 레거시 데이터의 복원 기준을 구분합니다.
한계
이름 경로는 이전 저장의 호환 수단입니다. 모든 이름 변경이나 중복 ID 문제를 자동 복구하지 않습니다.

저장 성능·안정성 수치

수치·규칙
핵심 저장은 동기 방식. 저장 지연·실패율 개선 수치는 미측정.
판독 기준
원본 기록의 진행 유지 결과와 재현 가능한 통계는 구분합니다.
한계
슬롯 크기, 저장 액터 수, 맵 전환 조건, 디스크 환경, 반복 횟수와 지연 분포가 있어야 정량 비교할 수 있습니다.

알려진 한계와 검증 범위

  • 저장은 동기 경로입니다. 비동기 작업 큐·원자적 파일 교체·임의의 동적 액터 재생성은 구현 범위로 주장하지 않습니다.
  • SaveGameSubsystem에는 GameMode 설정 의존이 남습니다. GameDataSubsystem의 최초 로드도 동기이며 설정 실패 시 GameMode 대체 경로를 확인해야 합니다.
  • GUID 유일성·기존 데이터 호환·복원 콜백 순서, UI 재진입·중복 구독, 서버·클라이언트 ASC 초기화는 각각 확인 대상입니다.
  • 이번 페이지 업데이트에서는 원본 분석 문서와 공개 설계 자료를 대조했습니다. 빌드·PIE·패키징·성능 시험을 새로 실행하지 않았습니다.
